 Created the real-world ROS 2 closed-loop equivalent.
Run it with:
bin/run_loop_ros2.sh "pick the red box and place in the bowl" --confirm-actions





Added:
- [run_loop_ros2_host.py](/home/alexis-martinez/Desktop/real-robot/scripts/run_loop_ros2_host.py)
- [run_loop_ros2.sh](/home/alexis-martinez/Desktop/real-robot/bin/run_loop_ros2.sh)
The real mode reuses the existing closed-loop state machine but:
- Captures aligned RGB-D data through the configured ROS 2 topics.
- Loads the AprilTag-derived overview intrinsics and cam_to_base.
- Disables Gazebo model queries and oracle position snapping.
- Uses overview depth for GroundingDINO object localization.
- Rejects detections without valid aligned depth instead of falling back to a guessed table plane.
- Publishes accepted poses through /perception/object_pose.
- Records full XYZ poses in each iteration?s debug.json under detected_object_poses.
- Falls back to the overview camera if wrist RGB-D or wrist TF is unavailable.
Topic overrides can be passed after the task:
bin/run_loop_ros2.sh "pick the cup" \
  --overview-image-topic /overview_camera/overview_camera/color/image_raw \
  --overview-depth-topic /overview_camera/overview_camera/aligned_depth_to_color/image_raw \
  --overview-info-topic /overview_camera/overview_camera/aligned_depth_to_color/camera_info \
  --wrist-image-topic /camera/color/image_raw \
  --wrist-depth-topic /camera/aligned_depth_to_color/image_raw \
  --wrist-info-topic /camera/color/camera_info \
  --max-steps 8
The implementation passed compilation, shell syntax, calibration loading, and ROS capture-contract tests. Robot execution was intentionally not started because the camera topics were not active.

For request 0989aa95-8fd7-4a09-b66f-2ee73c97a6d6, the orchestrator never received the plan. That UUID does not appear anywhere in its logs.
The orchestrator itself is currently healthy:
- Container: running.
- /vlm_robot_planner: present.
- /vlm_planner/ready: true.
- Other plans immediately before and after this failure were acknowledged and executed.
So this occurrence was loss of the one-shot injection message?not a lost ACK. The temporary publisher discovered the subscriber, published once, waited for an ACK, and exited. DDS graph discovery alone does not guarantee that the writer-reader connection is fully ready for reliable delivery.
How to check
Replace REQUEST_ID with the UUID from the error.
Check whether the orchestrator received it:
REQUEST_ID="0989aa95-8fd7-4a09-b66f-2ee73c97a6d6"

docker logs --since 30m vlm_ros2_real 2>&1 \
  | grep -C 5 "$REQUEST_ID"
Interpretation:
- No output: injection message never reached the callback.
- Plan acknowledgement ... accepted=True: plan was accepted; only the ACK was lost.
- accepted=False: it was explicitly rejected, usually because the node was busy or not ready.
Follow plan activity live:
docker logs -f vlm_ros2_real 2>&1 \
  | grep --line-buffered -E \
  "Plan acknowledgement|Injected plan|Task completed|task failed|Perception"
